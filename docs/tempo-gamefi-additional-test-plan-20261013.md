## 最小实施方式

在托管 daemon 的运营配置中增加可选、私有的测试授权文件引用；正常用户创建/运行 API 不接收此字段。文件绑定 `chainId=42431`、当前 loopback origin、上述 owner、原 Actor IDs、基线计数 3、累计上限 9、6 局/120 次游戏调用/61440 输出 tokens/600000 raw 奖池和独立授权 UUID。固定到期时间不超过批准后 24 小时，并早于原任务剩余期限；文件摘要及初始计数在开始前落独立 journal。

`loadHostedDaemonConfig` 验证链、origin、owner 和文件权限；`HostedService.command` 在同一现有串行持久 admission 中使用“默认 3 + 有效授权的有限追加”判断。实际累计 `sponsoredOwners` 继续由已有新游戏 admission 自然从 3 增至 9，原 UUID 命中缓存时不增加计数。不直接编辑 database，不重置 `sponsoredTotal`，也不提供可重复领取的授权接口。无授权、错误 owner/链、过期或达到累计上限时仍拒绝新局。

同一份授权 journal 记录每个新 UUID、支路、调用/usage、奖金和消费，运行器在每次派发前检查累计硬上限；不更改 `live.ts` 的规则、模型策略、响应解析、赢家或牌堆。前端从有效运营授权投影显示本次追加额度与剩余局数，不让默认“3 局”文案和真实限制冲突。到期或额度耗尽后不再允许新增游戏，原历史及原 UUID 读取/恢复仍保留。

只针对授权边界、并行 admission/重复 UUID 不重复占额、Unknown 保留名额、到期与费用上限做回归；父 Agent 独立审查后再按用户批准的额度实跑。终局后重新核对全部签名角色 nonce、直接 Moonshot 与 Magpie 两个调用域、可信回放、真实 Tempo 收据和桌面/手机读取。

不建议换 owner、手工改累计计数、直接发奖励额度或重跑直到胜利：这些会绕过原成本限制，且无法证明真实游戏奖励消费。上述显式单次授权保持既有 Actor、原失败和真实累计计数，改动范围更小，也可逐局停止。
